# 优化日志

记录 `Optimize` 分支每一轮优化**为什么这么改**、改了什么、验证到什么程度。逐条提交流水见 [CHANGELOG.md](../CHANGELOG.md)。

---

## 一、背景与约束

项目是一个纯前端户型装修工具，整个应用只有 `index.html` 一个文件：2D 用 SVG 手绘平面图，3D 用 Three.js 生成场景，两者共享同一份 `state`，数据存 `localStorage`。

动手前确认了三条约束：

1. **方向**：补齐功能 + 提升交互效率，不是把它做成专业 CAD；
2. **形态**：保持现有的单文件结构、配色与交互风格，不做工程化重构；
3. **分支**：所有改动只进 `Optimize`，不合并 `master`。

这三条决定了很多取舍——例如明知拆成模块更好维护，但拆了就不再是「双击即用」，所以没拆。

## 二、动手前的诊断

先通读 2674 行代码，并把它跑起来（Docker + 浏览器实机）确认问题真实存在，再排优先级。

| 级别 | 问题 | 后果 |
| --- | --- | --- |
| P0 | 导入 JSON 只校验 `furniture` 是数组，不校验 `rooms[x].mat` | 非法材料键会让 `overviewPanel()` 抛 `TypeError`，右侧面板半死，需刷新恢复 |
| P0 | `setView()` 无 `try/finally`，`switching` 与 `body.busy` 只在成功路径复位 | WebGL 创建失败（禁用硬件加速、驱动异常）时，2D/3D 切换被永久锁死 |
| P1 | 只有贴墙吸附，没有家具之间的对齐 | 床与床头柜、沙发与茶几对不齐，只能靠肉眼 |
| P1 | 尺寸标注与 `WALLS` 双份维护，且只在初始化调用一次 | 换户型后标注不变，README 承诺的「改数据就能换户型」不成立 |
| P1 | 3D 默认机位写死，不随窗口宽高比调整 | 实测 712×817 窗口下，右侧休闲阳台被切掉 |
| P2 | Docker 镜像 `COPY` 静态文件、无挂载 | 改一行代码就要重建镜像，迭代成本极高 |
| P2 | 单文件 2674 行，2D/3D 靠全局变量互调 | 缺乏边界，改一边容易崩另一边 |

另有一批体验缺口（测量线只能全清、家具库无搜索、多选/锁定缺失）记入待办，不在本轮处理。

## 三、第一批：先修「会崩的」，再做「最影响手感的」

### 3.1 对齐辅助线

**动机**：布置类工具的评价分水岭不在功能多少，而在「摆得准不准、顺不顺手」。原实现只有贴墙吸附，家具之间毫无参照。

**做法**：
- 取当前家具的轴对齐包围盒（AABB），得到左 / 中 / 右三条竖线、上 / 中 / 下三条横线；
- 与其余家具的同类参考线两两比较，6 像素内吸附；
- 命中后画一条贯穿两者的虚线，松手即清。

**三个取舍**：
1. **墙面优先**。两个吸附同时存在必然打架。`snapMove()` 现在会回报本次是否由墙面命中，命中过的轴直接跳过家具间对齐——用户明确拖到墙边时，墙的意图更强。
2. **地毯不参与**。地毯面积大，参考线会覆盖整个房间，导致周围所有家具都往它身上吸。
3. **用 AABB 而不是旋转矩形**。视觉上用户看到的选中框就是 AABB，用它能保证「看到的线」和「吸附的线」一致；代价是旋转 45° 的家具吸附精度略低。

### 3.2 存档与导入校验

**动机**：文件导入是典型的不可信输入，而原实现是「能用就行」。一个非法键就能让整页渲染中断。

**做法**：`fixState()` 从「`Object.assign` 合并」改为白名单式逐字段重建——房间 id 与材料键必须在表内、墙类型必须合法、尺寸与坐标夹取上下限、颜色走正则、重复 id 重新生成。

**效果**：非法数据退化为「丢掉这个字段」，而不是「整页崩」。旧版存档里没有 `plan` 字段，也会在这里回落到默认户型，所以迁移是免费的。

### 3.3 3D 启动失败回退

**动机**：这不是理论问题。关闭硬件加速、远程桌面、老显卡都会让 `new WebGLRenderer()` 抛错，而原代码把它当成不会发生。

**做法**：`setView()` 包 `try/catch/finally`，失败时把 `viewMode`、`m3d`、`is3d`、`busy` 全部复位，并给出明确提示；`init()` 的 `inited` 标记从函数开头移到末尾，避免「初始化失败但已标记成功」导致的重试崩溃。

### 3.4 迭代循环

Docker 镜像是 `COPY index.html` 且没有挂载，改一行就要重建。新增 `docker-compose.dev.yml`（8081，挂载工作文件）后，改完刷新即见。**这是后面所有工作的前提**——没有它，每个改动都要等一次重建。

## 四、第二批：自定义户型与多方案

### 4.1 为什么必须先动数据层

户型数据原本是五个写死的常量数组，被 40 多处渲染代码直接引用。要支持编辑，只有两条路：

- **A. 全面重写**：把渲染函数改成接收 `plan` 参数。干净，但等于重写半个应用，回归风险极高。
- **B. 换数据源、保留引用**：把数据搬进 `state.plan`，让 `WALLS` 等变量变成「指向当前方案的引用」，`syncPlan()` 统一重指向。

选了 B。代价是保留了「全局可变引用」这个不够优雅的模式，收益是 **渲染代码零改动**，而且撤销/导入/换方案天然生效——因为状态快照本来就包含 `state.plan`。

### 4.2 编辑器交互

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 墙的输入方式 | 拖拽两点，自动轴对齐 | 矩形墙段占实际户型 95% 以上；斜墙需要任意角度碰撞与面积计算，成本不成比例 |
| 开洞方式 | 点墙体插入，参数在右侧面板 | 拖拽定宽更直观，但和「画房间」的拖拽手势冲突，容易误触 |
| 门开向 | 用点在多边形内判断，自动朝有房间的一侧 | 省的每次开洞都要手动翻；代价是暂时不能手动改 |
| 房间 | 手绘矩形 | 自动识别墙体围合需要多边形搜索 + 处理墙厚与缺口，出错率高、用户也无法干预 |
| 删除墙体 | 连带删除其上的门窗 | 否则门窗会悬空，3D 里更明显 |
| 尺寸标注 | 自定义户型退化为总开间 / 总进深 | 原来那套分段尺寸是照原户型图写死的，硬套到新户型上必然错 |

### 4.3 一个被忽略的坑：洞口没有真正「开」

第一版做完，开洞只是新增了一个窗元素，墙体本身是完整的。默认户型的墙**本来就是按门窗分段绘制**的，所以这个缺陷在默认户型上完全看不出来，只有在自定义户型里，3D 才会把整面墙糊在窗户前面。

修复方式：`addOpening()` 在插入洞口的同时，把宿主墙沿洞口切成两段，与默认户型的分段方式保持一致。同时把两处默认户型专用的飘窗过梁从自定义户型里排除。

**教训**：数据结构的约定如果只体现在「数据长什么样」而不体现在「代码怎么维护它」，新增写入路径时一定会漏。

### 4.4 多方案

存储从「一个 state」变成「一组方案 + 当前指针」：

```js
huxing-plans-v1 = { current: 'p1', list: [{ id, name, state, updatedAt }] }
```

- 旧键 `huxing-design-v1` 在首次加载时迁移成「方案 1」，不会丢数据；
- 切换方案先保存当前，再深拷贝目标方案的 state，避免两个方案共享同一个对象引用；
- **切换时清空撤销栈**：跨方案撤销会让人删掉另一个方案里的东西，风险大于便利。

## 五、第三批：规则一致性、性能与洞口编辑（2026-10-29）

**规则一致性**：补上了上一轮复查发现的三个「自相矛盾」——承重墙能开门洞、Esc 提示与实现不符、户型编辑下仍显示家具浮动条。另外，开洞会清空拆除记录这件事改成明确提示。

**性能**：两处写放大。一是 `save()` 原本每次序列化全部方案，改成「索引 + 单方案」两组键 + 250ms 防抖，切换/删除等关键操作强制落盘；二是拖动家具时每次 `pointermove` 都重建全部家具 SVG，改成只更新该节点的 `transform`，松手后再整体重绘。

**洞口编辑**：选中窗/门/推拉门后可改宽度、改类型、翻转门向、删除。改宽度的难点在于墙体在插入时就被切开了，所以必须同步伸缩两侧邻墙的内边，并把缩到零宽的墙清掉；否则洞口和墙之间会留缝或残留零宽墙体。

验证方式受了点限制：浏览器窗口变大后截图与 DOM 快照都不可用，于是在页面里临时挂了一段自检脚本，直接调用真实函数并跑完整条链路（改宽 → 换类型 → 翻转 → 删除 → 四次撤销复原），结果写进 `document.title` 读回。验证完已移除，没有留在产物里。

## 六、第四批：部署层与镜像重建（2026-10-29）

这一批没有碰业务代码。起因是「8080 上还是旧版本」——它不是 bug，而是 8080 跑的是 15 小时前构建的镜像，8081 才是挂载工作区的开发容器。但顺着这条线检查部署层，发现两个真问题：

**① 单文件应用的缓存没有策略。** 整个应用只有一个 `index.html`，没有文件名哈希可用。nginx 默认不给 HTML 发 `Cache-Control`，浏览器于是按启发式规则自行决定缓存多久（通常取 `Last-Modified` 距今的 10%）。后果是发版后用户可能长时间访问到旧版本，而且**没有任何征兆**——页面能打开、能操作，只是功能对不上。这比"加载慢"危险得多，因为它会被误判成代码 bug。

**② 健康检查在拉整页。** `HEALTHCHECK` 探的是 `/`，而首页是 700 KB+ 的单文件，每 30 秒完整下载一次。健康检查应该只验证 nginx 在服务，不该验证整页内容。

改法：

| 项 | 处理 |
| --- | --- |
| 缓存 | `index.html` 加 `Cache-Control: no-cache`（允许缓存，但每次回源校验；命中 304 时几乎零开销） |
| 健康检查 | 新增 `/healthz` 只回 `ok` 并关闭该路径的访问日志，`HEALTHCHECK` 改探它 |
| 安全头 | `server_tokens off`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN` |
| 压缩协商 | `gzip_vary: on`，让 CDN / 中间层能正确区分压缩与未压缩版本 |
| 构建上下文 | `.dockerignore` 补 `.workbuddy` / `docs` / `CHANGELOG.md` / `docker-compose.dev.yml` |
| 镜像元数据 | 标签改用 OCI 标准（`org.opencontainers.image.*`） |

顺带修了一个隐患：`docker-compose.dev.yml` 没有声明项目名，开发容器与生产容器落在同一个 compose 项目里，因此每次 `docker compose up` 都会报「找到孤儿容器」，而一旦有人习惯性加上 `--remove-orphans`，**开发容器就会被删掉**。现在声明 `name: floorplan-3d-dev`，两个项目彻底分开。

### 刻意没做的三件事

- **没有改多阶段构建**：这个项目没有编译产物要搬运，`COPY` 两个文件就完事了，多一层 stage 只增加理解成本。
- **没有锁 `nginx:alpine` 的小版本**：没有可回归的构建产物，锁版本带来的维护成本大于收益。如果以后引入构建步骤（比如把 three.js 打进镜像），那时才值得锁。
- **没有把 three.js 自托管**：这是部署层能做的、价值最高的一件——现在内网或断网环境只剩 2D 可用。但它要改 `index.html` 的 importmap 与资源路径，属于业务代码改动，不该混进一次「只动部署层」的提交里，留到下一批。

### 验证

重建后做了三方哈希比对：**工作区文件、容器内文件、HTTP 实际响应**三者 md5 一致（`04cf68c8…`），这比"看页面能打开"更可靠——能打开不代表装的是新代码。同时抽查了六个只存在于最新提交里的标识（`data-door`、`flipDoor`、`setOpenWidth`、`startWallDrag`、`brandName`、`planStates`），全部在服务端产物中命中。

响应层：`/healthz` → `200 ok`；`Cache-Control: no-cache`、`nosniff`、`SAMEORIGIN` 均生效；gzip 后 241 576 B → 79 834 B（33.0%）；`nginx -t` 通过；容器 `Up (healthy)`。浏览器实测 8080 首屏正常。

一个环境细节记在这里：在 Git Bash 下 `docker exec ... md5sum /usr/share/nginx/html/index.html` 会失败，因为 MSYS 会把容器内的绝对路径改写成 Windows 路径，需要加 `MSYS_NO_PATHCONV=1`。第一次比对时我误以为文件不存在，实际是路径被改了。

## 七、第五批：漫游模式（2026-10-29）

用户只说「漫游模式有 bug」，没说现象。这类反馈最忌讳猜——猜错方向改半天，改的地方还不是他碰到的。所以先用页面内自检把运行时的真实状态读出来：出生点、碰撞数、按键状态、连续 90 帧的位移。

第一次测就拿到了明确的数字：**不按任何键，1.5 秒位移 1.4 米**。一帧不多一帧不少，正好是 1.4 m/s 的步速 —— 说明有键一直「按着」。

### 两个必然会踩到的问题

**① 按键状态跨模式残留。** `keys` 是全局对象，只在 `keyup` 时清理。但「按住 W → 按 Esc 解锁指针 → 切走窗口」这条路上，`keyup` 可能永远收不到，于是 `keys.KeyW` 一直是 `true`。下一次进漫游，相机就开始自己往前走。这类 bug 最麻烦的地方是**不可复现**：只有先按住方向键再中断，才会出现。

修法是三处统一清理：切模式、指针解锁、窗口失焦。另外把速度向量一起归零——否则平滑处理会让残留速度再滑一小段。

**② 出生点写死。** 原代码是 `camera.position.set(wx(4200), 1.6, wz(8755))`，注释写着「入户门外」。在默认户型上没问题，但前几轮刚支持了自定义户型，这个坐标对新户型毫无意义：可能落在墙体内部、楼外空地，甚至户型之外很远的空白处。点「漫游」后看到的是一面贴脸的墙或一片白地。

改成从当前户型推导，三级回退：

1. 有入户门 → 站在门外 1m，朝门内看（门开向取反就是门外方向）；
2. 没有门 → 最大房间的中心，朝房间内侧；
3. 都没有 → 户型包围盒中心。

每个候选点都用 `blocked()` 校验，取第一个不卡墙的。这样默认户型仍然从入户门进，自建房也不会掉进墙里。

### 四个次级问题

- **剖切档位被污染**：进漫游强制 `cut = H`，退出不还原。鸟瞰用 1.2m 剖切的人，进一次漫游回来墙就全立起来了。改成进出配对。
- **门碰撞段长写死 0.9m**：实际门宽 785/880/890/893mm。窄门会多挡 11.5cm，贴着门框走像撞上空气墙。改成在门对象上存实际长度。
- **移动没有惯性**：每帧直接把速度顶到满速，起步收步都是瞬移。改成指数平滑（时间常数约 70ms），松手后滑行约 9cm。
- **`e.target.matches` 可能抛错**：`keydown` 的 target 不一定是 Element。这类问题平时不出现，一旦出现就是整页报错，顺手补上类型判断。

### 一个测试自身踩的坑

自检第一版用的是 `joy.x/joy.y`（触屏摇杆），但没给摇杆输入，`mag < .05` 直接 return，测出来「位移 0」——差点误判成「走不动」。改用键盘 `keys` 注入才拿到有效数据。

这件事的教训写在这里：**验证时"没有变化"要先怀疑验证手段，再怀疑被测代码**。同一个道理，自检里两次报错（`MATS` 里没有 `tile` 键、经典脚本里访问模块作用域的 `OX`）都是测试数据写错，不是产品缺陷。

### 验证

页面内自检 + 浏览器真实交互两条路径都跑过：3D 场景 → 漫游 → 点遮罩锁定指针（准星出现）→ `Esc` 暂停 → 鸟瞰，并确认「剖切墙」档位在进出后仍然高亮、墙体仍是剖切状态。具体数值对比见 [CHANGELOG](../CHANGELOG.md) 中 `8094f36` 一节。

## 十、已知限制

1. 只支持轴对齐矩形墙段，画不了斜墙、弧形墙；
2. 房间靠手绘矩形，不会自动识别墙体围合出的区域，也不支持 L 形房间（默认户型的 L 形房间来自种子数据）；
3. 洞口可以改宽度和类型、门可以翻转开向，但还不能拖动改位置；
4. 删除洞口后墙上会留缺口（墙体已在插入时断开），需要撤销或手动补墙；
5. 自定义户型的尺寸标注只保留总开间 / 总进深；
6. 拖动家具仍可压墙、穿墙（无碰撞），松手不会自动推出；漫游时家具同样不挡人，会穿过床与沙发；
7. 窄屏（约 712px）顶栏会涨到 5 行。
